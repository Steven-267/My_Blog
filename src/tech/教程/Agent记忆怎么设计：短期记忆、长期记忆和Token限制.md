# Agent 记忆怎么设计

做 Agent 的同学，迟早会碰到一个问题：

**为什么这个系统刚刚还记得用户说了什么，过一会儿就像失忆了一样？**

这背后其实不是“模型突然变笨”，而是记忆设计本身就没有做好。

很多 AI 应用在 Demo 阶段只需要几轮对话，问题不明显；但一旦真正进入业务场景，用户会自然期待系统具备连续性，比如：

- 记得我上一次说到哪了
- 记得我的偏好
- 记得已经确认过的事实
- 不要每轮都让我重复背景

这时候，记忆就不是锦上添花，而是体验核心。

## 先分清两种记忆

我一般会把 Agent 的记忆分成两类：

- 短期记忆
- 长期记忆

这两个词听上去很像，但解决的是完全不同的问题。

## 1. 短期记忆：保证一次任务能接着往下走

短期记忆主要解决“当前这次会话别断片”。

它通常会包含：

- 最近几轮对话
- 当前任务状态
- 已经调用过的工具结果
- 中间生成的草稿或推理结果

这些信息最典型的特点是：

- 对当前任务强相关
- 生命周期短
- 过一段时间就可能失效

如果是 LangGraph 场景，这类内容就很适合放在 `state` 里；如果是服务层实现，也可能存在内存或 Redis 里。

## 2. 长期记忆：跨会话保留用户和业务事实

长期记忆解决的是“这次会话结束后，哪些信息值得以后继续记住”。

例如：

- 用户画像
- 身份信息
- 已确认的偏好
- 已经达成共识的业务事实
- 可复用的经验规则

这类信息不适合只留在临时上下文里，而更适合：

- 先抽取
- 再结构化
- 最后落到数据库或知识存储中

到了下一次会话，再根据用户 ID、当前上下文和问题去召回最相关的部分。

## 为什么不能把所有历史都塞给模型

这是很多系统一开始会走的路：

“既然模型有上下文窗口，那我就把全部历史都传进去。”

这种做法短期能跑，但很快就会遇到问题：

- token 成本越来越高
- 时延越来越大
- 噪声越来越多
- 重要信息反而被淹没

所以记忆系统的目标，从来不是“存得越多越好”，而是：

**在合适的时候，把最有用的信息带回来。**

## 一个更合理的记忆设计思路

我比较认可的方式是分层处理：

### 最近几轮，直接保留

这部分最相关，也最容易影响当前回复。  
通常可以直接放进上下文。

### 更早历史，做摘要

当对话变长时，可以把前面的内容压成摘要，只保留关键结论、已确认事实和未完成事项。

### 需要长期保留的信息，做结构化存储

比如：

- 用户喜欢什么风格
- 账号属于哪个公司
- 已经确认过哪些业务参数

这些内容最好抽成字段，而不是继续躺在一大段原始对话里。

### 真正需要时，再做召回

不是每次都把所有长期记忆喂给模型，而是根据当前问题去匹配最相关的部分。

这跟 RAG 的思想其实是一致的。

## 短期记忆里最容易踩的坑

### 1. 全量历史无脑拼接

这样做最直接的问题就是上下文膨胀。

而且历史越长，旧信息越可能干扰当前判断。

### 2. 任务状态和对话内容混在一起

比如用户自然语言消息、工具结果、审批状态、草稿内容全堆在一起。  
时间一长，系统自己都难以维护。

更好的方式是把它们拆开管理：

- 对话历史一类
- 工具结果一类
- 任务状态一类
- 用户事实一类

## 长期记忆里最容易踩的坑

### 1. 什么都记

如果系统把所有对话内容都当作长期记忆，存储会迅速膨胀，而且很多信息根本没有复用价值。

长期记忆更适合存：

- 稳定偏好
- 已确认事实
- 高复用规则

而不是每一句临时闲聊。

### 2. 不做结构化抽取

原始文本直接存下来当然最快，但后面检索和使用会非常痛苦。

比如“用户偏好深色界面”这种信息，如果不抽成结构化字段，后续系统很难稳定利用。

### 3. 召回没有过滤条件

没有用户 ID、业务场景、时间范围等过滤条件，系统很容易召回到不属于当前上下文的旧信息。

这比“忘记”更危险，因为它会让系统看起来像是“记错了”。

## token 限制怎么解决

这个问题其实不是单点技巧，而是一个组合策略。

我更常用的做法有这几个：

- 保留最近 `n` 轮对话
- 对更早历史做摘要
- 对可复用内容做向量化或结构化
- 真正需要时再召回

如果再往前走一步，还可以把一些稳定能力沉淀成：

- skills
- profiles
- rules
- memory stores

这样每次进入对话时，不是重新从海量历史里找，而是直接从已经整理过的知识单元里取。

## 一个简单的工程视角

如果用更后端一点的语言来描述，我会把 Agent 记忆看成三层：

```text
实时上下文层 -> 摘要压缩层 -> 长期记忆检索层
```

这三层分别对应：

- 当前轮次必须知道什么
- 较早历史如何低成本保留
- 跨会话哪些事实值得长期记住

这样设计的好处是清楚、可控，也更容易扩展。

## 总结

我一直觉得，Agent 的“聪明感”很大一部分不是来自模型参数，而是来自记忆系统是否设计得足够好。

用户真正感知到的不是：

- 模型是不是最新版本

而是：

- 它记不记得我是谁
- 它记不记得我们刚说到哪
- 它会不会重复问已经确认过的问题

所以记忆设计的核心，不是存得多，而是存得准、取得到、上下文用得住。

如果只记一句话，那就是：

**短期记忆保证连续性，长期记忆保证延续性，而 token 限制要求我们必须学会压缩和召回。**

把这三件事想清楚，Agent 才会真正开始像一个“会持续协作的系统”。
