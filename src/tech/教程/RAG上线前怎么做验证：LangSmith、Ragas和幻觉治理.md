# RAG 上线前怎么做验证

很多团队做 RAG，最开始关注的是：

- 检索接上了没有
- 模型能不能回答
- 页面能不能跑通

但真正一到上线阶段，问题就会变成另一种：

- 这个答案到底准不准？
- 它是不是在胡说？
- 换一版 Prompt 或分块策略之后，到底是变好了还是变差了？

如果这些问题没有答案，RAG 系统其实还没有准备好上线。

所以我一直觉得，RAG 不是“接上向量库就结束”，而是还需要一整套验证和治理方法。

## 先分清两类幻觉

我一般会把 RAG 的幻觉分成两类：

### 第一类：没检到，模型硬答

这种情况通常是检索阶段就已经失败了。  
系统没有拿到真正相关的材料，但模型又没有老老实实说“不知道”，而是继续凭语感补全。

### 第二类：检到了，但总结跑偏

这种情况更隐蔽。  
上下文里明明有答案，但可能因为检索不够准、上下文混杂、Prompt 约束不够，最后生成阶段还是发生了偏移。

把这两类分开看很重要，因为它们的治理手段不完全一样。

## 没有评测集，很多优化都只是错觉

很多 RAG 调优看起来很忙：

- 改 chunk 大小
- 换 embedding
- 接 rerank
- 调 Prompt

但如果没有固定评测集，最后就很容易陷入一种状态：

**每次都觉得“好像更好了”，但说不出到底好在哪里。**

所以第一件事不是继续拍脑袋调，而是先准备一套评测样本。

我更偏向准备这样的数据：

- 用户问题
- 标准答案或参考答案
- 希望命中的关键知识点
- 是否允许回答“不知道”

这套数据不一定很多，但一定要有代表性。

## LangSmith 更像一个实验平台

如果团队已经在用 LangChain 或 LangGraph，那 LangSmith 会非常顺手。

我对它的理解不是“一个评分工具”，而是：

**一个可以管理数据集、跑实验、比较版本、看链路的实验平台。**

它比较适合做这些事情：

- 把测试题做成 dataset
- 跑不同版本的 RAG 流程
- 对比不同 Prompt、不同 chunking、不同 rerank 的效果
- 查看线上真实样本的回放

通俗一点说，LangSmith 像一个“考试平台”：

- 题是你自己出的
- 考生是你的不同 RAG 版本
- 评分规则也可以自己定义

这对工程落地非常有价值，因为你终于可以把“感觉”变成“对比”。

## Ragas 更像一组专门给 RAG 准备的评分指标

如果说 LangSmith 更像实验平台，那 Ragas 更像评委工具箱。

它比较有代表性的能力包括：

- 忠实度
- 答案相关性
- 上下文相关性

这几个指标为什么重要？

### 忠实度

看的是：  
**答案里的结论能不能从给定上下文推出。**

这能直接帮助我们识别“模型是不是编了”。

### 答案相关性

看的是：  
**答案有没有真正围绕用户问题展开。**

有时候模型说得很多，但并没有真正回答问题。

### 上下文相关性

看的是：  
**系统检索出来的内容，和这个问题是否真的相关。**

这能帮助判断问题到底出在检索还是生成。

## 我更推荐的评测思路

在真实项目里，我更倾向于把两类方式结合起来：

- 用自建标注集保证业务贴合度
- 用 LangSmith 管实验和回放
- 用 Ragas 或自定义 evaluator 去做评分

因为仅靠通用指标，往往不够懂你的业务；
但如果完全只靠人工抽查，又很难长期规模化。

比较稳的做法是：

```text
业务样本 + 平台化实验 + 自动评分 + 人工抽检
```

## 幻觉治理，我通常会分 4 层做

### 1. 先把检索质量做上来

这是第一层，也是最容易被低估的一层。

包括：

- 文档清洗
- 合理分块
- 去重
- metadata 补充
- 混合检索
- rerank

很多幻觉，看起来是“模型胡说”，本质上其实是“没把该给它的材料给到它”。

### 2. 在生成阶段收紧约束

Prompt 里要明确告诉模型：

- 只能基于检索结果回答
- 没有依据就说不知道
- 不允许自由补充事实

这一步不能解决所有问题，但能明显减少“检不到还强答”的情况。

### 3. 输出时尽量带引用

我非常建议让回答尽量附带依据片段、来源标题或者章节信息。

它的价值不只是“让用户更信任”，更重要的是：

- 方便排查
- 方便审计
- 方便判断答案是否有支撑

很多团队只有在线上事故之后，才意识到“可溯源”有多重要。

### 4. 高风险场景加额外校验

比如金融、医疗、合同、客服投诉这类场景，光靠一次生成是不够的。

通常还需要：

- 规则兜底
- 事实校验
- 敏感分类
- 人工审核

这里一定不要抱幻想，觉得“模型已经很强了，应该能自己解决”。

工程上更可靠的思路永远是：

**高风险场景，不把正确性完全押在模型一次输出上。**

## 评测时，我会重点看哪些指标

如果要做一个更实用的观察面板，我会优先关注这些：

- Recall@K / Hit@K
- 最终回答准确率
- 幻觉率
- 格式正确率
- 平均响应时延
- token 成本

如果只看“模型答得顺不顺”，很容易误判。

真实项目里，很多版本之所以不适合上线，不是因为回答太差，而是：

- 成本太高
- 时延太大
- 格式不稳定
- 长尾问题不安全

## 总结

RAG 做到后面，会越来越像一个系统工程，而不是一个单点技巧。

如果你让我用一句话概括：

**RAG 的上线标准，不是“它能回答”，而是“它能被验证、能被比较、出了问题能被追踪”。**

所以在我看来，真正值得投入的不是盲目换模型，而是把下面这几件事建立起来：

1. 固定评测集
2. 版本对比机制
3. 自动评分能力
4. 幻觉分层治理

把这套东西搭起来，RAG 才会从“能演示”，变成“能交付”。
