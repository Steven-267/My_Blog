# 流式输出模式怎么选

最近做大模型接口、日志实时展示或者双向聊天时，经常会碰到一个词：

**流式输出。**

很多人第一次接触时，会把它简单理解成“边生成边返回”。这个理解没有错，但还不够完整。因为真正落到工程里，流式输出其实至少要同时看三件事：

- 你用什么传输方式
- 你按什么粒度往外发
- 你中间有没有缓冲，以及什么时候 flush

如果这三层不分开看，选型时很容易混。

先看一张总览图。

![流式输出三层结构](/My_Blog/assets/images/streaming/streaming-layers.svg)

## 什么是流式输出

最简单的定义就是：

**数据不是等全部生成完再一次性返回，而是边生成边发送，客户端边接收边处理。**

它最核心的价值一般有两个：

- 降低首字节等待时间
- 提升实时感和交互体验

为什么大模型页面一旦改成流式，用户就会明显觉得“这个系统更聪明了”？  
本质上不是答案变好了，而是系统更早开始反馈了。

## 第一层：传输方式怎么选

### 1. HTTP Chunked

这是一种非常基础的流式思路，基于 HTTP 分块传输。服务端可以一块一块返回数据，客户端边收到边处理。

它的特点是：

- 不需要引入新协议
- 实现成本相对低
- 适合普通接口、大文本返回、下载场景

如果你只是想把一段较长内容分段吐出去，而不是做复杂实时交互，它已经够用了。

### 2. SSE

SSE，`Server-Sent Events`，是前端接大模型流式输出时非常常见的选择。

它的特点是：

- 服务端单向推送
- 浏览器侧接入简单
- 对“边吐文本边展示”的场景非常友好

所以很多网页里的 AI 打字机效果，背后就是：

- `SSE + Token 级输出`
- 或 `SSE + Chunk 级输出`

这也是我在网页展示大模型回复时最常见的默认推荐。

### 3. WebSocket

WebSocket 的核心优势不是“更流”，而是：

**它支持双向实时通信。**

这就决定了它更适合：

- 聊天系统
- 实时协同编辑
- 语音流
- 实时控制面板

如果你的系统不仅要服务端往外推，还要客户端持续发控制指令、回执、状态更新，那么 WebSocket 往往更合适。

### 4. gRPC Streaming

如果场景是服务和服务之间的高性能流式通信，那 gRPC Streaming 往往更值得考虑。

它更适合：

- 微服务内部高频推送
- 低延迟数据流
- 双向流式处理

和浏览器侧的 SSE、WebSocket 相比，gRPC Streaming 更偏后端和基础设施层。

## 第二层：输出粒度怎么定

很多人说“我要做流式输出”，但其实还没回答另一个关键问题：

**你准备按多细的粒度往外发？**

常见有 4 类。

### Token 级

一个 token 一个 token 往外发。  
实时感最强，打字机效果最明显。

缺点也很直接：

- 事件数更多
- 网络和渲染开销更高
- 服务端和前端处理频率更高

### Chunk 级

攒一小段再输出。  
这是我觉得最平衡的一种方式。

它通常兼顾了：

- 足够强的实时感
- 更稳定的吞吐
- 更低的事件风暴风险

### 行级

最常见于日志输出、终端程序。  
遇到一行，输出一行，用户很好理解。

### 消息级

一次推送一个完整事件。  
适合结构化事件流，比如：

- 任务开始
- 检索完成
- 工具调用成功
- 最终答案生成完毕

这类场景比“打字机效果”更重视事件语义。

## 第三层：缓冲策略别忽略

流式输出还有一层非常容易被忽略：

**不是你代码里 `send` 了，客户端就一定立刻收到。**

中间如果有缓冲，体验会完全不同。

### 无缓冲

有数据就尽量立即发。  
延迟最低，但系统调用频率更高。

### 行缓冲

遇到换行才输出。  
非常适合日志和 CLI。

### 全缓冲 / 块缓冲

缓冲区满了或者主动 flush 才发。  
吞吐更高，但实时性会变差。

这也是为什么有些接口明明“写了流式”，前端却还是最后一下子看到完整结果。  
问题不一定出在协议，可能出在缓冲层。

## 常见场景里的默认答案

如果你只想快速做工程选型，可以先记这张图。

![流式输出场景默认答案](/My_Blog/assets/images/streaming/streaming-defaults.svg)

把它翻译成一句更口语的话就是：

- 网页里展示大模型输出：优先 `SSE`
- 双向实时交互：优先 `WebSocket`
- 微服务内部高性能流式通信：优先 `gRPC Streaming`
- 终端日志或命令行输出：重点盯 `缓冲` 和 `flush`

## 如果你是 Java 工程师，最常见的落地方式是什么

如果是 Spring 体系，最容易上手的通常有两条路：

### 1. SSE

如果目标是网页里展示 AI 回复，SSE 基本是最顺手的方案。

一个很常见的写法是使用 `SseEmitter`：

```java
@GetMapping(path = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream() {
    SseEmitter emitter = new SseEmitter(0L);

    Executors.newSingleThreadExecutor().submit(() -> {
        try {
            emitter.send(SseEmitter.event().name("message").data("第一段内容"));
            emitter.send(SseEmitter.event().name("message").data("第二段内容"));
            emitter.send(SseEmitter.event().name("message").data("第三段内容"));
            emitter.complete();
        } catch (IOException e) {
            emitter.completeWithError(e);
        }
    });

    return emitter;
}
```

这个例子不复杂，但足够说明本质：

- 服务端不是等全部内容生成完才返回
- 而是分多次把数据推给客户端

### 2. WebSocket

如果你的系统里除了“服务端往前端推”，还需要：

- 用户实时发控制消息
- 房间内多人协同
- 状态双向同步

那 WebSocket 往往比 SSE 更自然。

## 大模型场景里，为什么 SSE 这么常见

因为它刚好满足了这几个条件：

- 浏览器支持好
- 前端接入成本低
- 单向输出很符合大模型回答的主路径
- 能很好做出逐字或逐段展示效果

所以你会经常看到一句很典型的话：

**大模型网页流式输出，默认先想 SSE。**

这不是说它永远最好，而是说在“大模型单向往前端吐文本”这个问题上，它通常是最低阻力路径。

## 真正上线时，还要注意 3 个坑

### 1. 代理层缓冲

有时候你的应用层已经在流式发数据了，但网关、代理、Nginx 还在帮你缓冲。

这时客户端体验就会变成：

- 服务端觉得自己在流
- 前端却觉得还是一次性返回

所以排查流式问题时，不要只看业务代码。

### 2. 前端读取方式不对

后端用了流式，不代表前端一定按流式消费。  
如果前端还是等完整响应体再处理，效果一样会被吞掉。

### 3. 粒度过细导致抖动

如果每个 token 都发一次，虽然“实时感”很强，但也更容易出现：

- 事件太频繁
- 页面频繁重绘
- 网络开销上升

很多时候，把 token 合成小 chunk 再发，整体体验反而更稳定。

## 最后怎么记最省事

我更推荐用一个三层模型去记：

### 第一层：传输方式

- HTTP Chunked
- SSE
- WebSocket
- gRPC Streaming

### 第二层：输出粒度

- Token
- Chunk
- 行
- 消息

### 第三层：缓冲策略

- 无缓冲
- 行缓冲
- 全缓冲 / 块缓冲

只要这三层不混，你对流式输出的理解就已经比很多“只记协议名”的场景清楚了。

## 总结

流式输出不是单一技术点，而是一组组合设计。

如果你问我最实用的一句话总结是什么，我会说：

**流式输出模式的本质，是在“传输方式、输出粒度、缓冲策略”三层之间做取舍。**

而如果你问我大模型网页最常见的默认答案是什么，那通常还是：

**SSE + Token / Chunk 级输出。**

先把这句话记住，再回头看 WebSocket、gRPC Streaming、日志 flush，你就不容易乱了。
