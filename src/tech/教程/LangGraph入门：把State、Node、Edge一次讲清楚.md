# LangGraph 入门

很多人第一次接触 LangGraph，都会觉得它的名词有点多：

- State
- Node
- Edge
- Command
- Checkpointer
- interrupt

看文档时每个词都能看懂，但一组合起来就容易乱。

所以这篇文章我不打算按文档顺序复述，而是想用工程视角，把它整理成一句更好记的话：

**LangGraph 本质上是一个用“图”来组织 AI 工作流的框架。**

如果这句话先立住了，后面的概念就都好理解了。

## 为什么会需要 LangGraph

当我们的 AI 流程开始变复杂时，普通的“链式调用”很快就不够用了。

例如下面这种流程：

- 先判断问题类型
- 再决定要不要检索知识库
- 某些场景要调工具
- 高风险问题要人工审批
- 中间如果失败，还要支持恢复继续执行

这时候你会发现，流程已经不是一根线了，而更像一张图。

LangGraph 解决的，就是这种：

**有状态、可能分支、可能暂停、可能恢复的 AI 工作流。**

## 1. State：共享上下文

我觉得最好记的类比是：

**State 就是整个流程的一块公共白板。**

比如一个问答 Agent 的 State 里，可能有这些字段：

- question
- retrieved_docs
- tool_results
- answer

每个节点都能从这块白板上读数据，也能往上面写数据。

这样一来，我们就不用在函数之间传一长串参数，而是把“流程当前处于什么状态”集中管理起来。

如果你做过 Java Web 项目，可以把它粗略理解成一次流程执行期间的上下文对象。

## 2. Node：真正干活的步骤

Node 很好理解，它就是流程里的一个处理步骤。

比如：

- classify_question
- retrieve_docs
- call_tool
- generate_answer

每个 Node 都接收当前 State，做自己的事情，然后返回对 State 的更新。

所以我更喜欢把 Node 理解成：

**流程中的一个工位。**

每个工位只负责自己那一步，但都围绕同一份共享状态工作。

## 3. Edge：流程的路由规则

如果说 Node 是“干活的人”，那 Edge 就是“指路的路标”。

它负责决定流程下一步去哪。

最常见的两类是：

- 普通 Edge：固定从 A 到 B
- 条件 Edge：根据当前 State 决定下一步去哪

比如问题分类完成之后：

- 普通咨询，走检索
- 高风险请求，走人工审批
- 无法识别，直接结束

这就是典型的条件路由。

## 4. Reducer：多个更新怎么合并

这个概念一开始容易被忽略，但实际很重要。

Reducer 本质上是在回答一个问题：

**如果多个节点都更新同一个字段，最后怎么合并？**

比如两个并行节点都往 `docs` 里写内容：

- 如果是覆盖，后者会把前者盖掉
- 如果是追加，就可以把两个结果拼成一个列表

所以 Reducer 不是额外的花活，而是并行流程里必须明确的合并规则。

## 5. Command：既改状态，又改流程

我觉得 Command 最容易记住的方式是：

**它不是普通路由，而是一条“带控制意图”的运行时指令。**

什么时候用它？

当你不仅要决定“下一步去哪”，还要顺手更新 State 时，它就很有价值。

最朴素的记忆方法是：

- 只想决定路由，用 conditional edge
- 既想更新状态，又想跳转，用 Command

这个边界一旦想清楚，很多设计会自然清晰。

## 6. Checkpointer：流程自动存档

我一直觉得 Checkpointer 是 LangGraph 很工程化的一点。

它做的事情很像“自动存档”：

- 每一步执行完保存状态
- 按 thread 组织历史
- 支持暂停后恢复
- 支持失败后继续

如果没有它，很多 Agent 流程一旦中断，就得从头再来。

但接上 Checkpointer 后，系统就有了“可恢复执行”的基础。

这对真实业务非常关键。

## 7. thread_id：这次执行的档案号

thread_id 可以理解成：

**这一趟流程的唯一编号。**

为什么重要？

因为 Checkpointer 需要靠它知道：

- 当前状态属于谁
- 后续恢复应该接哪一条流程
- 历史记录应该查哪一份

没有 thread_id，很多“暂停再继续”的能力都无从谈起。

## 8. interrupt：先暂停，等人回来拍板

很多流程不是模型自己就能闭环的。

例如：

- 自动生成邮件，但发送前必须人工确认
- 自动审批建议，但需要运营最终点头
- 大额风险操作要人工复核

这时候 interrupt 就很有用了。

它的本质是：

**在某个节点中主动暂停执行，等外部输入回来后再继续。**

这个设计非常符合真实业务，因为很多流程本来就不是全自动的，而是“AI + 人”协作。

## 一个最容易理解的例子

比如“自动发邮件前先走人工审批”，我通常会这样理解：

State 里放：

- draft_email
- risk_level
- approval_result

Node 可能有：

- draft_email
- judge_risk
- human_review
- send_email

Edge 决定：

- 低风险直接发
- 高风险去人工审批

`human_review` 节点里可以触发 interrupt，暂停等待外部输入。  
之后外部再通过同一个 `thread_id` 恢复流程，系统继续执行。

这就是 LangGraph 这套概念真正组合起来后的样子。

## Java 工程师怎么理解它

如果你本身是后端工程师，我觉得可以把 LangGraph 理解成：

- 一套状态机式的工作流引擎
- 只是每个节点里干的事情，经常是 LLM 调用、工具调用或检索

所以它不是一个“神秘 AI 框架”，而是把传统工作流思想和 LLM 场景结合了起来。

你熟悉这些概念之后，再看它就不会觉得散：

- State 是上下文
- Node 是处理步骤
- Edge 是路由
- Reducer 是合并规则
- Command 是带控制意图的跳转
- Checkpointer 是持久化
- thread_id 是执行编号
- interrupt 是人工介入点

## 总结

我觉得学 LangGraph 最怕的是一上来记太多术语。

更好的方式是先抓住主线：

**它是在解决“复杂 AI 流程如何被清晰编排、被暂停恢复、被长期维护”的问题。**

当你把这件事想清楚，再回头看那些名词，它们就不再是零散定义，而是一套彼此配合的工程设计。

如果你以后要做：

- 多步骤 Agent
- 带人工审核的流程
- 可恢复的长任务
- 有状态的复杂工作流

那 LangGraph 确实值得认真学一下。
