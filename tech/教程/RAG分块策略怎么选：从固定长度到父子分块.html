RAG 分块策略怎么选

很多人做 RAG 的第一反应是：

  • 先选一个 embedding 模型
  • 接一个向量库
  • 然后把文档塞进去

但项目一跑起来，很快就会发现，真正决定效果上限的，往往不是“模型名字”，而是最不起眼的那一步：

chunking，也就是分块。

如果块切得不合理，后面检索、rerank、生成都会被一起拖垮。

这篇文章就聊一个最现实的问题：

RAG 里的文档到底该怎么切？

为什么分块这么重要

RAG 本质上是“先检索，再生成”。

而检索能不能拿到对的问题上下文，很大程度上取决于 chunk 是否刚好处于一个合适的粒度。

切太大，会有几个问题：

  • 一个 chunk 里信息太杂
  • 检索命中了，但噪声很多
  • token 成本偏高

切太小，也会有问题：

  • 语义不完整
  • 关键上下文被切散
  • 模型看到片段后无法判断其所属章节

所以分块策略做得好，本质上是在解决一句话：

既要让系统检得准，又要让模型看得懂。

常见的 4 类分块思路

1. 固定长度分块

这是最容易上手的一种方式，比如每 300 到 500 tokens 切一块，再加一点 overlap。

它的优点很直接：

  • 实现简单
  • 工程成本低
  • 很适合先做 baseline

但缺点也很明显：

  • 容易把一句话拦腰截断
  • 容易把表格、列表、代码块切碎
  • 不理解文档结构

所以它适合“先跑起来”，不太适合长期作为唯一方案。

2. 结构化分块

这是我更推荐的主力方案。

做法是按文档本身的结构切，比如：

  • 标题
  • 小节
  • 段落
  • FAQ
  • 表格
  • 代码块

这种方式的优势在于，它更符合人类写文档的组织方式。

比如一段接口说明，最好把：

  • API 路径
  • 参数说明
  • 返回示例

放在同一个 chunk 里，而不是简单按字符数切开。

3. 语义分块

语义分块更像“按话题边界切”。

它对长篇叙述型材料尤其有用，比如：

  • 培训手册
  • 政策解读
  • 长篇知识文档

优点是语义更完整，缺点是：

  • 实现复杂度更高
  • 需要额外模型或规则辅助
  • 调试成本更高

如果团队还在做第一版 RAG，我一般不会上来就选它做主方案。

4. 父子分块

这是我自己非常喜欢的一种思路。

它通常是：

  • 小块负责召回
  • 大块负责补充上下文

比如先把文档切成很细的子块用于检索，命中后再把它所属的父块一起带给模型。

这样兼顾了两件事：

  • 小块更容易召回准
  • 大块能给模型更多完整上下文

它很适合长文档、制度文档和复杂技术说明。

我更推荐的默认方案

如果让我给一个更通用的工程默认值，我会选：

结构优先，token 兜底。

也就是说：

  1. 先清洗文档
  2. 再按标题层级、段落、列表等结构切
  3. 如果某个块还是太大，再按 token 限制继续细切

这样的好处是，既保留了文档结构，又不会让单块无限膨胀。

清洗比很多人想得更重要

在真正的企业文档里，脏数据非常常见。

比如：

  • 页眉页脚
  • 目录页
  • 水印
  • 重复段落
  • OCR 错字

如果不先清洗，分块做得再漂亮，后面检索质量也会被拖下去。

所以我通常会把流程做成这样：

原始文档 -> 清洗 -> 结构解析 -> 分块 -> metadata 补充 -> 向量化

这里面，“清洗”和“metadata 补充”常常比“换 embedding 模型”更值。

metadata 一定要保留

很多 RAG 效果差，不是检索不到，而是检到了以后系统不知道这个 chunk 来自哪里。

所以每个 chunk 最好都带上 metadata，例如：

  • 文档名
  • 章节路径
  • 页码
  • 来源链接
  • 文档类型

这些字段的价值很大：

  • 检索结果更容易解释
  • rerank 更容易利用结构信息
  • 回答时更容易溯源
  • 出问题时更容易排查

我自己很少做“只有文本，没有元数据”的知识库。

不同文档类型，分块策略也应该不同

这点非常重要。

FAQ

最适合按“一问一答”切。
一个问答就是一个 chunk，天然清晰。

接口文档

更适合按接口切。
不要把路径、参数、返回值分散到多个块里。

合同、制度、规范

更适合按条款切，并且保留“第几章、第几条”。

表格

不能直接横着切断。
最好把表头一起带上，或者转成结构化文本。

代码和技术文档

更适合按函数、类、模块说明切。
如果函数签名和解释分开了，回答效果通常会明显下降。

分块时最容易踩的几个坑

1. 只按字符数硬切

这是最常见的坑。
实现是简单了，但语义经常被切碎。

2. overlap 设置太大

很多人害怕信息丢失，就把 overlap 设得很大。

结果会带来几个问题：

  • 重复内容太多
  • rerank 结果被污染
  • 存储和检索成本上升

overlap 不是越大越好，而是够用就行。

3. 不保留标题路径

这会让 chunk 脱离上下文。

比如模型看到一句“支持增量同步”，如果不知道它属于“数据同步模块”的哪一节，这句话的解释空间会非常大。

4. OCR 脏数据不清洗

这一点会直接影响召回和生成。
尤其是扫描件、PDF、截图文档场景，影响特别明显。

如何判断你的分块有没有变好

这件事不能只靠感觉。

我更建议看这些指标：

  • Recall@K / Hit@K
  • 最终回答准确率
  • 幻觉率
  • 平均上下文长度
  • token 成本

很多时候，项目效果提升最大的不是“换大模型”，而是：

  • chunking 调整对了
  • metadata 更完整了
  • rerank 接上了

这些基础工作做好，RAG 往往会稳很多。

总结

如果你刚开始做 RAG，我给的建议其实很朴素：

  1. 先别追求最花哨的分块算法。
  2. 先把清洗、结构化切分和 metadata 做扎实。
  3. 把固定长度分块当 baseline，而不是终点。

如果用一句话收尾：

好的分块策略，不是把文档切开，而是把“可检索性”和“可理解性”同时保留下来。

这件事做对了，RAG 才真的算站稳第一步。
