Prompt 怎么写得更稳定

这两年很多同学都开始做 AI 应用，但真正落到工程里之后，很快就会发现一个问题：

Prompt 不是“把需求写清楚”这么简单，而是要让模型长期稳定地按同一种方式输出。

如果只是自己本地试玩，回答差一点也能接受；但一旦接到 Java 服务里，后面还要解析 JSON、做链路监控、记录审计日志、加业务兜底，这时候 Prompt 是否稳定，直接决定这个功能是不是能上线。

这篇文章不讲玄学，只讲我觉得最实用的 6 个习惯。

1. 一个 Prompt 尽量只做一件事

很多不稳定，根源不是模型不行，而是 Prompt 太贪心。

比如一个 Prompt 里同时要求模型：

  • 判断用户意图
  • 检索知识库
  • 生成最终回复
  • 判断是否转人工

这种设计在 Demo 阶段看起来很省事，但到线上一般都会变得非常脆。

更稳的做法是拆步骤：

  • 一个 Prompt 只做分类
  • 一个 Prompt 只做信息抽取
  • 一个 Prompt 只做最终生成

这样做的好处非常明显：

  • 输出目标单一，模型更不容易跑偏
  • 每一步都能单独评测
  • 出问题时更容易定位是哪一层出了问题

如果用后端工程的思路去看，其实这和“单一职责”是一样的。

2. 把上下文分区，而不是一股脑塞进去

很多 Prompt 看起来很长，但真正的问题是“信息没分层”。

业务规则、用户问题、历史对话、知识库内容全混在一起，模型很容易把“规则”当“素材”，或者把“示例”当“事实”。

我比较建议把上下文拆成几个明确区域，例如：

### 任务说明
### 用户问题
### 历史对话
### 参考资料
### 输出要求

这样做的意义不是好看，而是帮助模型建立“这段内容是什么角色”的边界感。

尤其在 RAG 或 Agent 场景里，这一点特别关键。因为一旦边界不清楚，模型就可能把历史对话里的猜测，当成知识库事实来复述。

3. 约束要写清楚，而且要有优先级

工程里的 Prompt 不能只说“请准确回答”，这没有约束力。

真正有用的是把规则写成可以执行的形式，比如：

  • 只能依据给定材料回答
  • 材料不足时明确返回“不知道”
  • 涉及高风险问题时必须保守处理
  • 输出格式错误时视为失败

如果场景再复杂一点，我还会把优先级也写出来：

安全规则 > 业务规则 > 格式规则 > 风格要求

为什么这很重要？

因为模型面对多条要求时，不一定会自动理解哪条更重要。你不写优先级，它就会自己猜；一旦让模型自己猜，结果通常就不稳了。

4. 能结构化输出，就不要只要自然语言

这是我最想强调的一点。

如果后面还有程序要消费这段结果，就尽量别让模型输出一大段散文式回答，而是直接要求结构化格式。

例如：

{
  "intent": "",
  "sub_intent": "",
  "need_human": false,
  "confidence": 0.0,
  "reason": ""
}

这类输出对工程非常友好：

  • Java 服务更容易解析
  • 字段可以校验
  • 结果可以落库
  • 更容易做回放和监控

真实项目里很多“模型不稳定”，最后排查出来其实不是答案质量差，而是字段缺失、格式漂移、枚举值乱写，导致后面的链路接不住。

所以 Prompt 工程有时候不是在和“智能程度”较劲，而是在和“可集成性”较劲。

5. few-shot 不用多，关键是校正边界

很多人一听 few-shot，就会想到“多给几个例子”。

其实重点不是多，而是准。

我更喜欢在下面几种情况加示例：

  • 类别边界容易混淆
  • 某些场景必须走特殊分支
  • 文本抽取格式很严格
  • 用户说法非常口语化

比如客服分流里，“我要退钱”和“你们怎么退款”虽然相近，但一个可能是强诉求，一个可能只是咨询。
这时候给 2 到 5 个边界样例，往往比继续堆规则更有效。

few-shot 最有价值的地方，不是告诉模型“答案长什么样”，而是告诉它：

什么算这一类，什么不算。

6. 上线后不要只靠感觉调 Prompt

很多 Prompt 调优失败，问题不在 Prompt，而在调法。

如果每次一口气改三四处，再凭肉眼看几条结果说“好像变好了”，这种做法很难沉淀经验。

更稳的方式是：

  • 给 Prompt 做版本管理
  • 准备一批固定评测样本
  • 每次只改一个变量
  • 观察准确率、格式正确率、幻觉率、时延和 token 成本

这和我们做接口性能优化、本地缓存策略优化其实是同一个思路：

先建立基线，再单变量实验。

没有评测的 Prompt 调优，本质上和“拍脑袋改参数”差不多。

一个我更推荐的 Prompt 模板

如果是工程场景，我会更偏向下面这种组织方式：

你是一个工单分类助手。

【任务】
根据用户问题判断一级意图、二级意图，以及是否需要转人工。

【输入】
用户问题：{query}
历史对话：{history}
知识库：{kb}

【规则】
1. 只能依据输入内容判断，不允许编造不存在的信息。
2. 如果信息不足，返回“无法判断”。
3. 涉及退款、投诉、账号安全，优先标记为需要转人工。
4. 输出必须是合法 JSON，不要附加解释。

【输出格式】
{
  "intent": "",
  "sub_intent": "",
  "need_human": true,
  "confidence": 0.0,
  "reason": ""
}

这个模板不一定适合所有场景，但它体现了几个通用原则：

  • 任务明确
  • 输入边界清楚
  • 规则可执行
  • 输出可消费

Java 工程师为什么尤其要重视这件事

如果你本身是 Java 程序员，Prompt 稳定性其实是很容易共情的。

因为我们天然会关心这些事情：

  • 下游能不能稳定解析
  • 出错时能不能兜底
  • 调整版本后会不会回归
  • 有没有监控指标能观察

Prompt 看起来像文案，但真正上线之后，它其实更像一种“软规则代码”。

只是这段代码不是跑在 JVM 里，而是跑在模型里。

总结

我一直觉得，Prompt 工程最容易让人误判的一点是：
它看起来像写文字，所以很多人以为它不需要工程方法。

但恰恰相反。

越是要进生产环境，越要把 Prompt 当成工程对象来管理。

如果你只记住这 3 句话，也够用了：

  1. 一个 Prompt 尽量只做一件事。
  2. 规则、上下文、输出格式一定要分清楚。
  3. 调优不要凭感觉，要靠样本和指标。

把这三件事做好，很多“模型怎么又抽风了”的问题，都会提前消失。
